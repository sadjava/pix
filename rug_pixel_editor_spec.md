## 0. Инструкция coding-агенту

Реализуй продукт по этапам, указанным в разделе 15. Не пытайся генерировать всё приложение одним большим изменением. После каждого этапа запускай тесты, TypeScript-проверку и production-сборку; исправляй регрессии прежде, чем двигаться дальше.

Перед началом работы:

1. Изучи существующий репозиторий, если он уже создан. Не удаляй и не переписывай существующий код без причины.
2. Создай `IMPLEMENTATION_PLAN.md`, где перечислены модули, этапы, риски и команды разработки.
3. Создай `DECISIONS.md` и записывай туда принятые технические решения, если приходится отступить от этого ТЗ.
4. Выдели слой хранения данных и слой синхронизации в отдельные интерфейсы. Редактор должен работать без авторизации и без доступности удалённого API.
5. Не добавляй обязательные сетевые запросы во время старта редактора, открытия холста, рисования или локального сохранения.
6. Не считай сохранение завершённым до подтверждения успешной записи в IndexedDB. Не показывай статус облачной резервной копии до подтверждения сервера.
7. Не помещай секреты или service-role-ключи в клиентский код, `VITE_*`, исходники, конфигурацию сборки или репозиторий.
8. Не заменяй уже работающую реализацию фиктивными заглушками, если переходишь на следующий этап.
9. Любая новая возможность должна иметь критерии приёмки и тесты, относящиеся к ней.
10. В конце каждого этапа укажи: что сделано, какие файлы изменены, команды проверки, результат тестов, известные ограничения и следующий этап.

Если требование неоднозначно, выбери вариант, который не ведёт к потере пользовательских данных, документируй решение и продолжай без блокировки разработки.

## 1. Цель продукта

Создать персональный редактор пиксельных узоров для дизайна ковров. Один пиксель сетки соответствует одной клетке рисунка. Пользователь должен иметь возможность создавать несколько проектов, раскрашивать клетки пальцем или стилусом, строить геометрические фигуры, применять симметрию, выделять и копировать области, экспортировать изображение с сеткой и без неё.

Главное требование: приложение должно быть **offline-first**. Оно остаётся полноценным редактором без подключения к интернету. В редкие моменты, когда интернет доступен, оно автоматически отправляет резервный снимок проекта по HTTPS в закрытое облачное хранилище. Облако — страховка, а не источник, от которого зависит работа приложения.

## 2. Принятые продуктовые решения

- Формат первого релиза — PWA, устанавливаемая на главный экран Android-планшета из браузера.
- Публикация статической части — GitHub Pages; код приложения не содержит пользовательские рисунки.
- Рисунки и рабочее состояние хранятся локально в IndexedDB.
- На старте приложение не требует аккаунта. Резервное копирование в облако включается после настройки аккаунта и подключения.
- Для первой облачной реализации использовать Supabase Auth + закрытое хранилище снимков + таблицу метаданных с RLS. Реализовать провайдер через интерфейс, чтобы его можно было заменить без изменения редактора.
- В первой версии облако — **резервные копии и восстановление**, а не совместное редактирование и не полноценная двусторонняя синхронизация между несколькими устройствами.
- Вся обычная работа должна быть доступна без экспорта в файл. Импорт/экспорт файлов — дополнительная возможность переносимости и аварийного восстановления.
- Язык интерфейса первой версии — русский. Текст интерфейса должен быть централизован, чтобы добавить другие языки позже.
- Целевое устройство — современный Android-планшет с актуальным Chrome/Chromium. Десктопный браузер используется для разработки и отладки.

## 3. Объём функциональности

### 3.1 Обязательный функционал первой полноценной версии

1. Галерея нескольких холстов: создать, открыть, переименовать, дублировать, удалить.
2. Настраиваемые размеры холста в клетках.
3. Карандаш, ластик, заливка связной области, пипетка.
4. Линия, окружность, прямоугольник и ромб.
5. Вертикальная и горизонтальная симметрия, а также обе одновременно.
6. Перемещаемые оси симметрии с привязкой к клетке или границе между клетками.
7. Прямоугольное выделение, отображение ширины/высоты в клетках, копирование, вырезание, вставка и перемещение.
8. Независимые отображение Grid и Checkerboard.
9. Палитра цветов, выбор цвета, добавление/редактирование/удаление цветов.
10. Undo/Redo, сохранение рабочего состояния и разумная история действий.
11. Автосохранение локально, индикаторы состояния сохранения и обработка ошибок хранилища.
12. PWA-установка, загрузка app shell и запуск без сети после первого онлайн-запуска.
13. Автоматическое облачное резервирование, индикатор последней успешной копии и восстановление версии.
14. PNG-экспорт с независимыми настройками сетки и шахматного фона.
15. Экспорт/импорт проекта в JSON для аварийной копии и переноса.

### 3.2 Не включать в первую версию

- Совместное редактирование несколькими пользователями.
- Коллаборативные курсоры, комментарии и шаринг проектов по публичной ссылке.
- Слои и сложные маски.
- Текстуры, кисти с непрозрачностью, антиалиасинг и свободное векторное рисование.
- Расчёт материалов/стоимости ковра. Архитектуру не следует усложнять ради этих возможностей.
- Обязательную регистрацию для локальной работы.
- Нативный Android APK на первом этапе. Возможность завернуть PWA в Capacitor остаётся потенциальным будущим направлением.

## 4. Технологический стек и структура

### 4.1 Рекомендуемый стек

- React + TypeScript + Vite.
- HTML Canvas 2D для холста; не создавать DOM-элемент на каждую клетку.
- IndexedDB через небольшую библиотеку-обёртку, предпочтительно Dexie или эквивалент с понятной миграцией схемы.
- `vite-plugin-pwa` / Workbox для precache app shell и сервис-воркера.
- Vitest для unit/integration-тестов; Playwright для браузерных E2E-тестов, если окружение доступно.
- Supabase JS SDK только в слое резервирования. Данные локального редактора не должны зависеть от SDK.
- GitHub Actions для автоматической сборки и публикации на GitHub Pages.

Версии зависимостей фиксировать lock-файлом. Агент должен сверить требования выбранных актуальных версий, не устанавливать пакеты «наугад» и не использовать неподдерживаемые API без обоснования.

### 4.2 Предлагаемая структура каталогов

```text
src/
  app/                 # запуск приложения, маршрутизация, состояния
  components/          # панели, диалоги, кнопки, уведомления
  projects/            # галерея, операции с проектами
  editor/
    canvas/            # viewport, преобразование координат, отрисовка
    tools/             # pencil, eraser, fill, line, circle, rect, diamond
    symmetry/          # оси и отражения клеток/фигур
    selection/         # выделение, clipboard, перемещение
    history/           # undo/redo, журнал действий
    palette/           # палитра проекта
  data/
    db.ts              # инициализация IndexedDB
    repositories/      # проекты, снимки, журнал, настройки
    migrations/        # миграции схемы данных
    autosave/          # очередь локального сохранения
  backup/
    provider.ts        # интерфейс облачного провайдера
    supabase/          # реализация провайдера
    queue.ts           # очередь резервных копий
    restore.ts         # проверка/восстановление
  pwa/                 # офлайн-статус, обновление PWA
  export/              # PNG, JSON, сериализация и контрольная сумма
  styles/
  test/
```

Фактическая структура может отличаться, если агент документирует более удачную организацию. Не делай один гигантский `App.tsx`.

## 5. Модель данных проекта

### 5.1 Проект

Каждый холст — отдельный проект со стабильным `projectId` (UUID), не зависящим от имени. Рекомендуемые поля:

```ts
interface ProjectRecord {
  id: string;
  name: string;
  width: number;
  height: number;
  schemaVersion: number;
  documentRevision: number;
  createdAt: string;
  updatedAt: string;
  lastOpenedAt: string;
  lastLocalSavedAt: string | null;
  lastCloudBackupAt: string | null;
  syncState: 'local-only' | 'pending' | 'uploading' | 'backed-up' | 'error' | 'conflict';
  localChecksum: string | null;
  cloudRevisionId: string | null;
  preview?: Blob | ArrayBuffer;
}
```

Поля можно адаптировать, но локальные и облачные ревизии должны различаться явно.

### 5.2 Содержимое холста

Содержимое проекта включает:

- ширину и высоту в клетках;
- состояние каждой клетки;
- палитру цветов с устойчивыми ID и HEX/RGBA-значениями;
- настройки Grid и Checkerboard;
- настройки симметрии и координаты осей;
- параметры отображения/последний viewport (необязательно синхронизировать viewport);
- дату/версию формата.

Предпочтительно хранить клетки компактным бинарным представлением, например `Uint16Array`/`ArrayBuffer` с индексом цвета и зарезервированным значением для пустой клетки. В сериализаторе необходимо явно документировать кодирование пустоты и палитры. Если выбрана другая схема, сравни её по объёму, простоте миграции и скорости отрисовки.

**Не хранить только PNG.** Рисунок должен оставаться редактируемой клеточной сеткой. PNG является экспортом и миниатюрой, но не источником истины.

### 5.3 Ограничения размеров

- Размер по умолчанию: 100 × 100 клеток.
- Пользователь может задать размеры при создании и изменить их с понятным подтверждением, если обрезается содержимое.
- В первой версии целевой рабочий диапазон — до 500 × 500 клеток; значения выше можно разрешать только после проверки памяти и производительности устройства.
- Не создавать отдельный DOM-узел на каждую клетку.
- При создании/изменении размеров учитывать квоту IndexedDB и показывать понятную ошибку, если сохранить проект не удалось.

### 5.4 Версионирование и миграции

У каждого документа должен быть `schemaVersion`. Миграции IndexedDB и JSON-проекта должны быть последовательными, проверяемыми и протестированными. Старый проект нельзя молча трактовать как формат новой версии. Если миграция не удалась, оставить исходные байты/снимок нетронутыми и показать ошибку с рекомендацией сделать резервную копию.

## 6. Редактор и пользовательский интерфейс

### 6.1 Общая компоновка

- Главный экран — галерея проектов «Мои ковры» с миниатюрами, размерами, датой изменения и статусом облачной копии.
- Экран редактора: холст занимает основную область; палитра и инструменты доступны рядом/снизу в зависимости от ширины экрана.
- На планшете интерфейс рассчитан на портретную и альбомную ориентацию.
- Интерактивные элементы достаточно крупные для касания; важные действия не требуют точного попадания в маленькие иконки.
- Иконки снабдить доступными названиями/tooltip/aria-label.
- Предусмотреть Undo/Redo, текущий цвет, активный инструмент, размеры сетки и статус сохранения.
- Диалоги удаления должны подтверждать потенциально необратимое действие, особенно если проект ещё не имеет облачной копии.

### 6.2 Управление холстом

- Один указатель (палец или стилус) — рисование/выделение активным инструментом.
- Два пальца — масштабирование и перемещение холста; жест не должен изменять клетки.
- Перемещение рабочей области мышью/трекпадом допустимо через отдельный режим или среднюю кнопку, если реализовано.
- Масштабирование должно быть относительно точки жеста, чтобы пользователь мог приблизить интересующую область.
- Холст и линии сетки остаются чёткими при масштабировании. Использовать device pixel ratio при настройке backing store Canvas.
- Приложение должно блокировать нежелательный скролл страницы на рабочем холсте, но не ломать доступность и прокрутку панелей.
- Корректно обрабатывать `pointercancel`, потерю фокуса, сворачивание страницы и смену ориентации.
- Координаты ввода переводить из экранных координат в координаты холста, затем в целочисленные координаты клеток. Не вычислять геометрию в CSS-пикселях.

### 6.3 Палитра

- Начальная небольшая палитра для быстрого старта.
- Выбор произвольного цвета (HEX и визуальный color picker).
- Добавление, переименование/изменение, удаление цвета с защитой от удаления цвета, используемого клетками, без явной стратегии замены.
- Опция замены всех клеток старого цвета новым при удалении/слиянии цвета.
- Пипетка считывает цвет клетки под указателем.
- Палитра и её порядок сохраняются в проекте.

## 7. Инструменты рисования

Все инструменты работают по клеточной сетке и используют текущий цвет, если ниже не оговорено другое.

### 7.1 Карандаш

- Одно нажатие меняет одну клетку.
- Движение указателя закрашивает все клетки по траектории без пропусков, даже если браузер пропускает промежуточные события.
- Использовать растеризацию сегмента (например, алгоритм Брезенхэма) между последней и текущей клеткой.
- Повторное попадание в клетку за один мазок не должно создавать лишние записи истории.

### 7.2 Ластик

Сбрасывает клетки в состояние пустоты/фона, не удаляя саму клеточную сетку. Если выбранная модель предусматривает цвет фона вместо пустоты, это должно быть однозначно отражено в модели данных и экспорте.

### 7.3 Заливка

- Заливка связной 4-соседней области одного цвета/состояния.
- По умолчанию 4-связность; диагональные клетки не считаются соседними.
- Реализовать flood fill без рекурсивного обхода стека вызовов, чтобы избежать переполнения на большой области.
- Заливка должна выполняться как одна операция Undo/Redo.
- При включённой симметрии заполнить соответствующие зеркальные области от всех уникальных отражённых seed-клеток. Не допускать дублирования записей.

### 7.4 Линия

- Указатель вниз задаёт начало, перемещение показывает предпросмотр, указатель вверх фиксирует конец.
- Использовать целочисленную растеризацию по клеткам; диагонали не должны иметь непредсказуемых пробелов.
- Вся линия — одна операция Undo.

### 7.5 Круг

- Первое нажатие задаёт центр, движение задаёт радиус, отпускание фиксирует форму.
- По умолчанию рисовать контур окружности на клеточной сетке.
- Реализовать симметричную растеризацию окружности, например midpoint circle algorithm; радиус округлять до ближайшего целого числа клеток.
- Отображать предпросмотр радиуса/окружности до завершения действия.
- Один круг — одна операция Undo.

### 7.6 Прямоугольник

- Первое нажатие — первый угол; движение — противоположный угол; отпускание завершает фигуру.
- Контур по умолчанию; если добавляется режим залитой фигуры, переключатель должен быть явно виден.
- Размеры считаются включительно по клеткам.

### 7.7 Ромб

- Первое нажатие задаёт центр; движение задаёт одну из вершин/радиус.
- Первая версия: ромб с вершинами по горизонтали и вертикали (диагонали параллельны осям сетки).
- Контурная растеризация без пропусков; preview до фиксации.
- Если выбран иной жест, документировать его в интерфейсе и тестах.

### 7.8 Общие требования к фигурам

- Геометрия формируется в клеточных координатах.
- В процессе жеста изменяется только временный preview; данные проекта не должны загрязняться каждым кадром отрисовки.
- После завершения применяется итоговый набор клеток атомарно.
- Изменения ограничиваются границами холста; отражённые за границей клетки игнорируются.
- Симметрия применяется к итоговому набору клеток фигуры.
- Каждая фигура — единая операция истории.

## 8. Симметрия

### 8.1 Режимы

- Выключена.
- Вертикальная.
- Горизонтальная.
- Вертикальная + горизонтальная.

Каждую ось можно отдельно перемещать по холсту. Ось может проходить по центрам столбцов/рядов клеток или по границе между ними.

### 8.2 Модель оси

Использовать координату в пространстве сетки, где границы клеток имеют целые координаты, а центры клеток — полуцелые. Хранить ось без округления до экранных координат; практичный вариант — хранить удвоенную координату `axis2` как целое число. Тогда ось может быть как на границе, так и в центре ряда/столбца.

Для столбца `c` отражённый столбец вычисляется из координаты центра клетки: `cMirror = axisX2 - c - 1`; аналогично для ряда. Для центра клетки `axisX2` нечётно, для границы между клетками — чётно. Проверить формулы тестами на крайних, центральных и внецентровых осях.

### 8.3 Перемещение осей и интерфейс

- Ось показывается поверх холста, но не экспортируется в рисунок.
- Ось можно двигать перетаскиванием; попадание по линии должно быть удобным даже при сильном увеличении/уменьшении.
- Кнопки смещения двигают ось с шагом половины клетки либо дают отдельный выбор: «по центру клеток» / «между клетками».
- Оси не должны незаметно перескакивать при изменении масштаба.
- Возможность скрыть линии осей, не отключая симметрию.
- Настройки симметрии сохраняются в проекте.

### 8.4 Семантика отражения

- Карандаш/ластик: изменить набор клеток и все его уникальные отражения.
- Линия/круг/прямоугольник/ромб: сначала растрировать исходную фигуру, затем отразить множество изменяемых клеток. Это предотвращает расхождение формы при зеркалировании.
- Заливка: вычислить отражённые seed-клетки; отдельно выполнить flood fill в соответствующих целевых областях, затем объединить наборы изменяемых клеток и применить одной операцией.
- Не применять изменение одной клетки многократно, если отражения совпали на оси.
- Если отражённая клетка лежит за границей холста, игнорировать её.
- Выделение/копирование/вставка в первой версии не отражаются автоматически; они работают буквально. Симметрия продолжает действовать на последующие операции рисования после вставки, но вставленное содержимое вставляется один раз. Если это создаёт UX-неоднозначность, интерфейс временно показывает статус «Симметрия не применяется к вставке».

## 9. Выделение и буфер обмена

### 9.1 Выделение

- Прямоугольное выделение по клеткам.
- Рамка и прозрачный/шахматный preview выбранной области.
- Панель/подпись показывает `Ширина × Высота` в клетках.
- Размер считается включительно: от столбца 10 до 19 — 10 клеток.
- Выделение можно отменить без изменений рисунка.

### 9.2 Операции

- Копировать: копировать в внутренний буфер данные клеток и нужную палитру/сопоставление цветов.
- Вырезать: скопировать, затем обнулить исходные клетки одной операцией истории.
- Вставить: preview, перемещение, подтверждение; вставка не меняет источник буфера.
- Повторная вставка разрешена.
- Перемещение выделения переносит содержимое с очисткой исходной области и записью в новую позицию одной транзакционной операцией истории.
- Если область выходит за границы холста, применять только пересечение с границами и показывать визуальную индикацию clipping.
- При вставке из другого проекта автоматически сопоставлять цвета по HEX; при отсутствии цвета добавлять его в палитру проекта без дублирования уже существующих совпадающих HEX.
- Внутренний clipboard хранится в памяти и может дополнительно сохраняться в IndexedDB, чтобы пережить перезапуск приложения. Если сохраняется, включить `schemaVersion` и восстановление.

## 10. Grid, Checkerboard и экспорт

### 10.1 Grid

- Тонкая линия по границе каждой клетки.
- Независимый toggle.
- Отображение сетки не изменяет данные рисунка.
- При низком масштабе допускается временно упрощать/скрывать часть линий для читаемости, но точный экспорт по сетке должен сохранять все линии согласно настройкам.

### 10.2 Checkerboard

- Шахматный фон — слой отображения для пустых клеток/проверки рисунка, не отдельный цвет рисунка и не изменение сетки данных.
- Размер клетки/блока checkerboard регулируемый; настройка отображения не меняет пиксели проекта.
- Опционально позволить задать размер блоков, по умолчанию 1 клетка.

### 10.3 PNG-экспорт

В диалоге экспорта задаются:

- показывать ли Grid;
- показывать ли Checkerboard;
- масштаб/размер результирующего PNG в пикселях на одну клетку;
- включать ли рамку вокруг холста (по умолчанию нет).

Экспорт строится из модели данных в отдельный offscreen canvas, а не через скриншот экрана. UI, панели и маркеры осей не экспортируются. Экспорт должен быть детерминирован: один и тот же документ и настройки дают одинаковое изображение.

- «Чистый рисунок»: без Grid и Checkerboard.
- «С миллиметровкой»: Grid включён.
- «С шахматным фоном»: Checkerboard включён; Grid по отдельному выбору.
- Клетки остаются резкими, без антиалиасинга при рендеринге базового пиксельного рисунка.

### 10.4 JSON-экспорт/импорт

- Экспортировать полный редактируемый проект, а не только bitmap.
- Включать `schemaVersion`, `projectId` (при импорте генерировать новый ID, если импортируется как отдельный проект), имя, размеры, палитру, клетки, настройки отображения и оси симметрии.
- Не включать токены авторизации, ссылки на приватные облачные объекты и секреты.
- До импорта валидировать структуру, версии и ограничения размеров. Отвергать некорректные файлы с понятным сообщением, без падения приложения и без изменения существующих проектов.
- Импорт по умолчанию создаёт новый проект; перезапись существующего требует явного выбора и подтверждения.

## 11. Локальное хранение и минимизация потерь

### 11.1 Обязательные гарантии

- Рабочий холст и галерея проектов работают без сети.
- Любая завершённая операция должна сохраняться локально автоматически.
- При длительном мазке приложение периодически фиксирует промежуточное состояние, чтобы внезапное закрытие/сбой не стирали весь мазок.
- Статус «Сохранено на устройстве» показывается только после успешного завершения транзакции IndexedDB.
- Ошибка записи никогда не должна молча скрываться; в интерфейсе есть предупреждение и повторная попытка.
- При `QuotaExceededError` не удалять автоматически проекты или резервные версии; показать понятную инструкцию освободить место/создать экспорт.
- По возможности вызывать `navigator.storage.persist()` и проверять `navigator.storage.persisted()`; результат показывать в диагностике/настройках. Отказ не должен блокировать приложение.
- Использовать `navigator.storage.estimate()` (если доступно), чтобы показывать примерный расход и доступное хранилище.
- Не обещать абсолютную гарантию сохранности браузерных данных: явная очистка данных/профиля или потеря устройства может уничтожить локальную копию. Облачная резервная копия снижает риск.

### 11.2 Сохранение операции

Рекомендуемая стратегия:

1. Все изменения сначала применяются к состоянию редактора.
2. Изменение каждой операции фиксируется в журнале (command/patch log) с последовательным номером, временем и типом.
3. В конце операции записывается её финальное изменение, обновляются документ и метаданные в одной IndexedDB-транзакции, где это возможно.
4. Во время длинного мазка делать checkpoint изменённых клеток примерно каждые 500 мс или после разумного порога изменённых клеток — выбрать и протестировать компромисс производительности/потери данных.
5. При восстановлении использовать последний валидный snapshot и применить подтверждённые записи журнала после него. Идемпотентно игнорировать уже применённые номера операций.
6. Периодически компактизировать журнал в снимок, не удаляя последний валидный снимок до завершения записи нового.
7. Состояние Undo/Redo хранить ограниченно и экономно (delta/patches, а не полные массивы на каждый шаг). Лимит истории настраиваемый в коде; разумный старт — последние 100 действий или ограничение по объёму. Undo/Redo после перезапуска должны восстанавливаться, если история сохранена; если лимит/сбой не позволяет восстановить полный стек, восстановить рисунок и безопасно очистить только недействительную историю с уведомлением.

Не использовать только debounce-сохранение всего документа после длительной паузы: при падении приложения последняя серия изменений может быть потеряна.

### 11.3 Несколько проектов

Все проекты, их метаданные, состояние редактора и журнал хранятся по `projectId`. При переключении проекта:

- зафиксировать текущую активную операцию;
- инициировать/дождаться локальной записи;
- переключить проект только после безопасной фиксации операции либо сохранить её как recoverable pending operation;
- при возврате восстановить данные и viewport проекта.

Удаление проекта локально должно быть двухшаговым при наличии ожидающих синхронизации изменений: сначала показать, что облачная копия отсутствует/есть, и предложить отмену или явное подтверждение удаления. Удаление локального проекта не должно автоматически физически удалять облачные версии без отдельного явного действия.

## 12. PWA и автономность

### 12.1 Установка и запуск

- Приложение опубликовано по HTTPS, имеет корректные Web App Manifest, название, иконки, цветовую тему и режим standalone.
- Пользователь может добавить его на главный экран Android-планшета.
- После первого успешного онлайн-запуска Service Worker кеширует все критические файлы приложения: HTML, JS, CSS, локальные шрифты/иконки, fallback-страницу.
- После успешной установки/кеширования приложение должно запускаться офлайн. Первый запуск/загрузка без сети до получения app shell не гарантируется и должен быть явно оговорён.
- Открытие галереи, создание и изменение проектов, все инструменты и локальное сохранение не должны зависеть от сетевых запросов.
- Облачные запросы изолированы в слое резервирования и не блокируют интерфейс.

### 12.2 Обновления PWA

- Новая версия не должна принудительно перезагружать открытый редактор посреди несохранённого действия.
- Показывать ненавязчивое «Доступно обновление»; устанавливать новую версию после явного выбора пользователя или после подтверждённого локального сохранения и безопасного завершения операции.
- Делать совместимые миграции схемы проекта. Не удалять старые кеши и структуры данных до успешной миграции и возможности восстановления.
- При обновлении Service Worker в офлайн-режиме продолжают работать уже закешированные файлы.

### 12.3 GitHub Pages

- Настроить `base` Vite согласно пути проекта GitHub Pages.
- Использовать GitHub Actions для проверки, сборки и публикации.
- Для SPA использовать HashRouter или другую совместимую с GitHub Pages стратегию, чтобы обновление/открытие ссылки не давало 404.
- Папка/ветка публикации не содержит проектов и резервных копий пользователя.
- Перед релизом проверить холодный старт в офлайн-режиме после ранее успешной установки и обновления.

## 13. Облачные резервные копии

### 13.1 Принципы

- Локальное сохранение имеет приоритет и никогда не ждёт ответа облака.
- Резервирование запускается при наличии сети, включённой опции backup и валидной сессии.
- Рисование не останавливается во время upload.
- На первом этапе синхронизация односторонняя: устройство → облачный архив версий. Восстановление из облака → локальный проект выполняется явным действием пользователя.
- Не удалять старые облачные версии автоматически до успешного создания новой версии и проверки целостности.
- Ошибки сети/авторизации/квоты показывать как проблему backup, но не как ошибку локального сохранения.

### 13.2 Провайдер

Первичная реализация — Supabase:

- Supabase Auth для владельца данных.
- Приватный bucket Storage, без публичных ссылок.
- Таблица метаданных backup-проектов/версий в Postgres.
- RLS политики на каждой таблице и на операциях Storage.
- Клиент использует только publishable/anon key, защищённый RLS; service-role key никогда не попадает в браузер.
- В репозитории хранятся миграции SQL и тесты разрешений.
- Все резервные копии принадлежат конкретному `user_id`; приложение не может читать, перезаписывать или удалять данные другого пользователя.
- Необходимость оплаты/условия бесплатного плана проверяются в настройках проекта перед production. На бесплатных планах сервис может иметь ограничения или приостанавливать неактивный проект; локальный функционал от этого не меняется.

### 13.3 Данные облачной версии

Снимок содержит редактируемый проект, а не только PNG. Рекомендуемые метаданные:

```ts
interface BackupVersion {
  backupVersionId: string;    // UUID, неизменяемый
  ownerId: string;
  projectId: string;
  localRevision: number;
  parentBackupVersionId: string | null;
  createdAt: string;
  schemaVersion: number;
  contentHash: string;        // SHA-256 от канонического/сжатого payload
  payloadSizeBytes: number;
  storageObjectPath: string;  // приватный путь, не публичный URL
  status: 'uploading' | 'verified' | 'failed';
}
```

Снимки должны быть неизменяемыми: новый backup создаёт новую версию/новый путь, а не молча перезаписывает старый объект. Использовать компрессию JSON/binary, если это оправдано, но восстановление должно проверять версию формата и checksum.

### 13.4 Протокол backup

1. Локально создать согласованный snapshot после сохранённой ревизии.
2. Вычислить контрольную сумму и размер.
3. Создать уникальный ID резервной версии и записать локальную задачу в outbox до отправки.
4. Отправить объект по приватному пути, уникальному для пользователя/проекта/версии.
5. Проверить успешный ответ и по возможности скачать/проверить метаданные объекта, затем зарегистрировать запись версии в БД.
6. Пометить версию `verified` и обновить локальные `lastCloudBackupAt`, `cloudRevisionId`, `syncState` только после успешного завершения необходимых шагов.
7. Если upload прошёл, а запись метаданных упала, повтор должен быть идемпотентным; не считать backup подтверждённым до завершения всего протокола.
8. Если сеть пропала, оставить outbox-задачу ожидающей и повторять с exponential backoff и jitter. Вручную доступна кнопка «Повторить резервное копирование».
9. Не хранить в памяти бесконечно несколько полных снимков. Outbox ссылается на локально зафиксированную ревизию или immutable payload; если локальная ревизия изменилась, старая задача всё равно должна завершиться либо быть безопасно заменена новой без потери последней версии.
10. Не запускать параллельные upload одного проекта без контроля порядка. По завершении более старой задачи нельзя пометить более новую ревизию как уже сохранённую.

### 13.5 Частота резервирования

Для первой версии:

- Создать backup после первой успешной локальной версии проекта, если пользователь вошёл в аккаунт.
- После изменений запускать debounce порядка 10–30 секунд, а также backup по событию ухода приложения в фон и при возвращении сети.
- Не отправлять новый полный snapshot чаще, чем нужно, если содержимое не изменилось.
- Если мазок продолжается, не считать промежуточный незавершённый backup последней устойчивой версией; можно использовать checkpoint, но backup-статус должен указывать revision, которую он покрывает.
- При ограниченной сети/квоте дать возможность выключить автоматический backup или отложить крупную загрузку, не выключая локальное сохранение.

### 13.6 Конфликты и восстановление

Первая версия не выполняет незаметное last-write-wins слияние. Если обнаружено, что remote head изменился относительно `parentBackupVersionId`, сохранить обе версии и пометить `conflict`.

В интерфейсе восстановления показывать имя, дату, размеры, размер снимка и идентификатор ревизии. Восстановление по умолчанию создавать новый локальный проект, а не перезаписывать текущий. Перезапись активного проекта возможна только через явное подтверждение после создания локального safety snapshot.

Поддержать действия:

- «Восстановить как новый проект»;
- «Сравнить дату/ревизии»;
- «Оставить обе версии».

Сравнение на уровне клеток можно отложить на будущую версию.

### 13.7 Безопасность и приватность

- Buckets приватные; проекты никогда не публикуются по общедоступной URL.
- RLS включён на всех экспонированных таблицах; добавить allow/deny тесты для anon/authenticated и чужого `user_id`.
- Включить HTTPS; не логировать содержимое рисунков, токены и пароль.
- Auth-сессия может отсутствовать/протухнуть; в этом случае локальный режим остаётся работоспособным, backup ждёт повторного входа.
- Если пользователь отключил backup, прекратить сетевые запросы для снимков, но не удалять автоматически уже сохранённые версии.
- Удаление всех облачных данных требует отдельного подтверждения и не выполняется при простом удалении локального проекта.

## 14. Состояния и сообщения пользователю

В UI должны быть отдельные состояния локального сохранения и backup; не сводить их к одному зелёному индикатору.

### Локальное состояние

- `dirty`: есть изменения в памяти;
- `saving-local`: локальная запись выполняется;
- `saved-local`: последняя подтверждённая ревизия находится в IndexedDB;
- `local-save-error`: запись не удалась, показать предупреждение и действие повтора.

### Облачное состояние

- `disabled`: резервирование не настроено/выключено;
- `pending`: локальная ревизия ждёт отправки;
- `uploading`: идёт передача;
- `backed-up`: конкретная локальная ревизия подтверждена сервером;
- `error`: резервирование не удалось, повторить позже;
- `conflict`: обнаружены разные головы версий.

Показывать пользователю время последней успешной облачной копии и какую локальную ревизию она покрывает. Если облако не доступно несколько дней, приложение должно продолжать работать, а в галерее — явно отмечать, что новые изменения ещё не резервированы.

## 15. Этапы реализации и критерии завершения

### Этап 0. Инспекция репозитория и план

**Сделать:** проверить структуру репозитория/окружение, выбрать зависимости, составить `IMPLEMENTATION_PLAN.md`, `DECISIONS.md`, настроить форматирование, lint, TypeScript и тесты.

**Готово, когда:** проект запускается; `npm run typecheck`, `npm run lint`, `npm test` и `npm run build` (или их эквиваленты) работают в CI. Если приложения ещё нет — создан каркас.

### Этап 1. Базовый холст

**Сделать:** Canvas, модель клеток, преобразование координат, масштабирование/перемещение, размеры холста, Grid, checkerboard preview, выбор цвета.

**Тесты:** перевод экранных координат в клеточные на нескольких scale/offset; крайние клетки; DPR; resize/rotate viewport.

**Готово, когда:** можно создать холст и закрасить/увидеть цветные клетки без дом-элементов на каждую клетку; zoom/pan не портят координаты.

### Этап 2. Локальные проекты и надёжное сохранение

**Сделать:** IndexedDB schema, repository слой, галерея проектов, создание/переименование/дублирование/удаление, автосохранение, статусы, persistent storage request, quota error handling, recovery journal/checkpoint.

**Тесты:** перезапуск страницы; offline; `QuotaExceededError`; закрытие во время длинного мазка; миграция схемы; повреждённая запись; переключение между проектами.

**Готово, когда:** все изменения автоматически восстанавливаются после обычного перезапуска, а ошибки записи явно отображаются. Нет обязательной сетевой зависимости.

### Этап 3. Карандаш, ластик, заливка, пипетка

**Сделать:** continuous stroke rasterization, eraser, flood fill, eyedropper, операция истории для каждого жеста.

**Тесты:** длинная диагональ без дыр; заливка однотонного большого холста; 4-связность; undo/redo; отсутствие повторных изменений одинаковых клеток.

**Готово, когда:** инструменты стабильны мышью, пальцем и стилусом; мазок отменяется единым действием.

### Этап 4. Undo/Redo и восстановление истории

**Сделать:** delta/patch-история; ограничения по размеру/числу операций; сохранение истории и восстановление после перезапуска; безопасная компактизация.

**Тесты:** последовательность paint → erase → undo → redo; undo после рестарта; история при нескольких проектах; аварийное завершение во время сохранения.

**Готово, когда:** история не хранит полную копию всего холста на каждое событие без обоснования; Undo/Redo применяет ожидаемые изменения.

### Этап 5. Симметрия

**Сделать:** режимы осей, позиция каждой оси, привязка к центру клетки/границе, перетаскивание и кнопки смещения; применение для карандаша/ластика/линии/круга/прямоугольника/ромба/заливки.

**Тесты:** отражение через клетку и между клетками; отражение на пересечении обеих осей; оси у краёв; off-canvas зеркала; уникальные клетки; fill на симметричных областях.

**Готово, когда:** результаты отражения определены точно и совпадают с формулами модели, независимо от масштаба.

### Этап 6. Геометрические фигуры

**Сделать:** line, circle by center+radius, rectangle, diamond, previews и одна history operation на фигуру.

**Тесты:** радиус 0/1/большой; линии по горизонтали/вертикали/диагонали; вырожденный прямоугольник; ромб с нулевым радиусом; симметрия фигуры; отмена во время/после preview.

**Готово, когда:** фигуры повторяемы и не оставляют артефактов при отмене или `pointercancel`.

### Этап 7. Выделение и копирование

**Сделать:** прямоугольное выделение, inclusive dimensions, copy/cut/paste, preview, move, clipping, palette mapping, сохранение clipboard при необходимости.

**Тесты:** размер выделения один пиксель; края холста; повторная вставка; копирование между проектами с разными палитрами; cut + undo; перемещение одной операцией.

**Готово, когда:** размеры всегда совпадают с числом клеток, область вставляется без смещения на одну клетку.

### Этап 8. Экспорт и импорт

**Сделать:** PNG по состоянию модели; grid/checkerboard toggles; размер на клетку; JSON export/import; валидация и миграции.

**Тесты:** чистый PNG; PNG с сеткой; PNG с checkerboard; корректное разрешение; повторный импорт; неподдерживаемая schemaVersion; повреждённый JSON; отсутствие секретов.

**Готово, когда:** импортированный проект редактируемый и визуально совпадает с исходным.

### Этап 9. PWA и публикация

**Сделать:** manifest, icons, service worker, precache app shell, offline fallback, корректный Vite base/SPA routing, GitHub Actions deployment, безопасный prompt обновления.

**Тесты:** после первоначальной загрузки включить авиарежим, принудительно закрыть приложение, открыть с домашнего экрана; открыть галерею и несколько проектов; проверить, что новая версия не сбрасывает текущую работу.

**Готово, когда:** все локальные сценарии редактора доступны офлайн, сетевые запросы не блокируют старт/рисование.

### Этап 10. Облачные резервные копии

**Сделать:** Auth (необязательный для локальной работы), интерфейс провайдера, Supabase adapter, приватный storage, SQL migrations, RLS policies/tests, outbox, snapshot compression/checksum, retries, version history, restore, conflict detection.

**Тесты:** backup онлайн; сеть пропала в середине upload; повторный upload; токен истёк; чужой `user_id`; upload успешен, metadata write упал; приложение перезапущено с pending outbox; восстановление в новый проект; старый backup не перезаписан.

**Готово, когда:** облачный статус выставляется только после подтверждения; сбой облака не влияет на локальное редактирование; снимки доступны только владельцу.

### Этап 11. Стабилизация и релиз

**Сделать:** пройти чек-лист раздела 16, проверить целевое устройство, производительность, доступность интерфейса и инструкции восстановления.

**Готово, когда:** критические тесты пройдены; нет потери проекта в проверенных аварийных сценариях; создана инструкция релиза и восстановления.

## 16. Обязательные тест-сценарии перед релизом

1. Создать три проекта, изменить каждый, перезапустить приложение офлайн — все три открываются с последними локально сохранёнными данными.
2. Рисовать 30–60 секунд непрерывным мазком, принудительно закрыть приложение в середине мазка, открыть снова — восстанавливается состояние не старше последнего checkpoint; интерфейс не заявляет сохранение неподтверждённых данных.
3. Выполнить десятки Undo/Redo, перезапустить приложение — проверить, что история и рисунок согласованы.
4. Начать работу онлайн, затем включить авиарежим. Создание/переименование проектов, рисование, выбор цвета, симметрия, геометрия, выделение, экспорт и локальное сохранение продолжают работать.
5. Создать локальные изменения офлайн, вернуть сеть — проект автоматически получает резервную копию без ручного экспорта и без остановки рисования.
6. Отключить сеть во время upload, вернуть сеть позднее — очередь повторяет попытку, подтверждённая копия корректна и дубликаты не повреждают состояние.
7. Удалить данные сайта/профиля в тестовом сценарии и восстановить проект из облачного backup после повторной аутентификации.
8. Попытаться получить чужую облачную копию через API — запрос отклоняется RLS; проверить anon, owner и чужой authenticated user.
9. Сымитировать заполненную квоту IndexedDB — пользователь получает предупреждение, приложение не сообщает «Сохранено» и не удаляет старые проекты автоматически.
10. Обновить опубликованную PWA при наличии несохранённой операции — обновление не приводит к потере/перезагрузке в середине операции.
11. Проверить ось через клетку и между клетками для одной и двух осей на нечётной и чётной ширине/высоте.
12. Проверить размеры выделения, включая 1×1, границы холста и прямоугольники, пересекающие края.
13. Импортировать повреждённый JSON и файл с неизвестной версией схемы — приложение не падает и не меняет существующие проекты.
14. Сделать несколько облачных версий проекта, затем испортить/удалить локальную версию; восстановить выбранную старую облачную версию как отдельный проект.

## 17. Нефункциональные требования

### Производительность

- Цель для 100 × 100 и 500 × 500: плавное рисование на целевом планшете в обычном режиме.
- Не перерисовывать всю модель без необходимости при каждом pointer event. Отделять canvas-слои (рисунок, grid, overlay/preview), если это улучшает производительность.
- Не выделять огромные временные массивы на каждом кадре.
- Заливка и вычисление фигур не должны блокировать интерфейс надолго; если вычисление тяжёлое, показывать состояние выполнения или переносить работу в worker после измерений.

### Надёжность

- Все обещания сохранения привязаны к реальному завершению транзакций/загрузок.
- Любая ошибка сохранения логируется технически (без содержимого рисунка и токенов) и показывается пользователю.
- Нет молчаливого удаления проекта, версии, outbox или журнала.
- Все destructive actions подтверждаются.

### Приватность и безопасность

- Локальный режим не требует аккаунта.
- Облачные данные закрыты по умолчанию.
- Использовать только HTTPS.
- Секреты не помещаются в клиентскую сборку.
- Не логировать пароли, access/refresh tokens, содержимое рисунков или личные данные.
- Проверить RLS отдельно automated tests.

### Доступность и UX

- Контрастные индикаторы, крупные targets, aria-label для иконок.
- Статусы выражаются не только цветом, но и текстом/иконкой.
- Критические предупреждения не исчезают сразу.
- Случайный тап не должен удалять проект/облачную копию без подтверждения.

## 18. Критерии готовности (Definition of Done)

Этап/функция считается готовой, только если:

- реализация завершена без заглушек;
- пройдены релевантные unit/integration/E2E-тесты;
- `typecheck`, `lint`, тесты и production build прошли;
- сценарий проверен в desktop browser и, когда касается сенсорного ввода/PWA, на Android-планшете или эмуляции touch;
- обновлена документация и `DECISIONS.md`;
- отсутствуют новые ошибки в консоли, утечки секретов и сетевые зависимости локального редактора;
- при работе с данными проверены сохранение, восстановление, ошибка и повтор.

## 19. Первое поручение агенту

Выполни только этап 0 и подготовку этапа 1. Сначала изучи репозиторий и предложи конкретный план с точными файлами/модулями и командами проверки. Затем реализуй минимальный каркас приложения и тестируемую модель холста. Не начинай облачную синхронизацию до того, как локальное сохранение и офлайн-старт спроектированы и протестированы.

Критический порядок приоритетов:

1. Данные не теряются при обычном закрытии/перезапуске.
2. Редактор полноценно работает без сети.
3. Инструменты дают предсказуемый результат.
4. Облачный backup надёжен и прозрачен.
5. Интерфейс красивый и удобный.

## 20. Справочные материалы

Используй официальную документацию для проверки деталей реализации и текущих ограничений сервисов:

- MDN — Storage API, квоты и удаление browser storage: https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria
- MDN — `navigator.storage.persist()`: https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/persist
- Vite PWA plugin: https://github.com/vite-pwa/vite-plugin-pwa
- Supabase Auth: https://supabase.com/docs/guides/auth
- Supabase Row Level Security: https://supabase.com/docs/guides/database/postgres/row-level-security
- Supabase Storage access control: https://supabase.com/docs/guides/storage/security/access-control
- Supabase billing / quotas: https://supabase.com/docs/guides/platform/billing-on-supabase
- Supabase Free project pausing: https://supabase.com/docs/guides/platform/free-project-pausing

Примечание по надёжности: IndexedDB и Cache API используют браузерное хранилище, чьи квоты и правила удаления зависят от браузера и устройства. Запрос persistent storage полезен, но может быть отклонён. Поэтому приложение должно честно отображать состояние локальной защиты и резервной копии, а не обещать абсолютную сохранность. Также бесплатный удалённый сервис может иметь лимиты, простой или паузу неактивного проекта; локальный режим при этом обязан продолжать работать.
